# Configuration

Every runtime knob lives in a single Pydantic `Settings` class — `shared/config.py`. Pydantic-Settings reads, in priority order:

1. process environment variables (`os.environ`)
2. `.env` file in the repo root
3. files inside `secrets_dir = "/run/secrets"` (file name == variable name)
4. the default declared on the field

`make bootstrap` writes a `.env` from `.env.example` and populates `.secrets-mock/` with the EdDSA keypair plus per-service passwords. Production deployments should swap that bind mount for real Docker Secrets, Vault, or SOPS-encrypted files.

Below is the full surface, grouped by concern. Required entries are marked **req**; everything else is opt-in.

## Database (Postgres)

| Variable           | Default                                                 | Notes                                       |
|--------------------|---------------------------------------------------------|---------------------------------------------|
| `DATABASE_URL`     | `postgresql+asyncpg://naso:naso@db:5432/naso`           | **req** in prod. Async driver only.         |
| `DB_POOL_SIZE`     | `20`                                                    | SQLAlchemy `pool_size`                      |
| `DB_MAX_OVERFLOW`  | `10`                                                    | SQLAlchemy `max_overflow`                   |

`bootstrap` injects the generated DB password into `DATABASE_URL` and writes the same value to `.secrets-mock/db_password.txt`, which docker-compose mounts as `POSTGRES_PASSWORD_FILE` for the Postgres container.

## JWT auth

The JWT keys are loaded **from `secrets_dir`** (file `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY`, no extension), not from `.env`. Setting an empty `JWT_PRIVATE_KEY=` in `.env` shadows the secrets-dir lookup — that's why `bootstrap` deliberately leaves the line out.

| Variable                     | Default                  | Notes                                                          |
|------------------------------|--------------------------|----------------------------------------------------------------|
| `JWT_PRIVATE_KEY`            | _(via secrets_dir)_      | Ed25519 PEM, generated by `cli/generate_secrets.py`            |
| `JWT_PUBLIC_KEY`             | _(via secrets_dir)_      | Ed25519 PEM                                                    |
| `ALGORITHM`                  | `EdDSA`                  | Whitelist of one — alg-confusion mitigated                     |
| `ACCESS_TOKEN_EXPIRE_MINUTES`| `60`                     | Cookie + Bearer lifetime                                       |
| `JWT_ISSUER`                 | `naso-forensic-engine`   | Becomes the `iss` claim                                        |
| `JWT_AUDIENCE`               | `naso-api`               | Becomes the `aud` claim, verified on decode                    |
| `JWT_LEEWAY_SECONDS`         | `10`                     | Clock-skew tolerance for `exp`/`nbf`/`iat`                     |
| `NASO_COOKIE_SECURE`         | `false`                  | Flip to `true` once you serve over HTTPS                       |

## Where to set what

- **Local dev**: edit `.env`. `make bootstrap` writes a working baseline; tweak from there.
- **Production**: don't ship `.env`. Inject the variables via your orchestrator (compose `env_file` + `secrets:`, Kubernetes `Secret`, ECS task definition, …). Keep the cryptographic material (JWT keypair, signing PEM) on a real secrets manager — Vault, AWS/GCP/Azure SM, SOPS — and mount it at `/run/secrets/<VAR_NAME>` so Pydantic picks it up automatically.
- **CI**: the workflow injects only the bare minimum (HS256 + dummy JWT material) so the test suite can run against in-memory SQLite. See [`.github/workflows/draconian-ci.yml`](https://github.com/fabriziosalmi/naso/blob/main/.github/workflows/draconian-ci.yml).

## Drift between docs and code

If you add a new field to `Settings`, also add it here. The contributing guide spells out the convention; the security-scan workflow doesn't yet enforce drift detection but a `pyproject.toml` dev-dep + a small `scripts/check_config_docs.py` is on the backlog.
